### 4-6. 테스트 코드 증가 — 리팩터·기능에 동반된 암묵적 작업

대부분의 `refactor`·`feat` PR에서 `__tests__/` 하위 신규/수정 파일이 함께 커밋됨. 예시: `selectDesktopRootIcons.test.ts`, `DOCProgram` 테스트 재작성(#44), Program Registry 테스트(#30) 등. 시간은 각 PR 환산치에 포함되어 있으나 분류표에서는 잘 드러나지 않아 별도 언급.

## 5. 수작업 환산 총합

| 카테고리 | 수작업 환산 (하한) | 수작업 환산 (상한) |
|---|---|---|
| 빌드/런타임 마이그레이션 | 122h | 220h |
| 아키텍처 리팩터링 | 114h | 204h |
| 디자인 시스템 | 48h | 76h |
| 공통 기반 | 36h | 64h |
| 기능 개발 | 88h | 148h |
| **합계 (메타 작업 제외)** | **408h** | **712h** |

> 상기는 "1인 숙련 풀타임 개발자 8h/일" 기준입니다. 실제 솔로 저녁·주말 리듬(주 18h)으로 환산하면 **23~40주 (약 5.5~10개월)** 분량입니다.
>
> 중앙값 **~500h** 기준으로 **38h 투입 = 약 13배**, 하한 408h 기준이면 **약 11배**. 따라서 **약 10~13배 (중앙값 13배)** 시간 효율. 이 숫자는 "같은 결과물을 완성한다면"이라는 가정이 깔려 있고, 솔로였으면 상당수 작업은 스코프를 줄이거나 시도하지 않았을 가능성이 큽니다.

### 5-1. 해석

- **"10~13배 빠르다"**보다 **"같은 시간에 10~13배 많은 일을 한다"**가 정확한 표현입니다.
- 기반 스택 교체만 해도 솔로로는 각각 별도 프로젝트로 분리해야 할 규모였으나, 2개월 안에 병행 처리됨.
- FSD → Feature-First 재편 등 **초반 번복** 작업도 환산 시간에 포함되어 있으므로 순수 "첫 시도에 맞춘 설계"를 가정하면 더 낮아질 수 있음.
- 반대로 말하면, 리팩터링 비중이 크기 때문에 같은 시간을 **제품 기능**에 쏟았다면 포트폴리오 콘텐츠가 훨씬 풍부했을 수도 있음. 트레이드오프.

## 6. Claude Code 사용 방식

### 6-1. 기본 워크플로

1. **브레인스토밍** — `superpowers:brainstorming` 스킬로 요구사항/옵션 탐색, 하드게이트로 사용자 승인
2. **설계 문서 작성** — `superpowers:writing-plans` + 프로젝트 전용 가이드 [`docs/rules/plan-writing-guide.md`](../rules/plan-writing-guide.md) 따라 `docs/plans/*.md` 생성
3. **구현** — `worker-implement-plan` 으로 설계 문서 기반 순차 실행
4. **검증** — `superpowers:verification-before-completion` 로 완료 주장 전 증거 확인 (pnpm tsc, pnpm test 등)
5. **PR 생성** — `worker-create-pr` 로 프로젝트 표준 템플릿 사용
6. **리뷰 루프** — `orchestrator-review-loop` 가 `worker-review-code` → `worker-resolve-review` 순환을 관리
7. **마무리** — `superpowers:finishing-a-development-branch` 로 머지 옵션 결정

### 6-2. 자체 구축 스킬 (9종)

| 스킬 | 역할 |
|---|---|
| `convention-commit` | `git commit` 직전에 [`commit-convention.md`](../rules/commit-convention.md) 로 라우팅 |
| `convention-frontend` | src/ 작업 시 topic별 규칙 문서로 라우팅 |
| `convention-plan` | `docs/plans/*.md` 작성 시 guide로 라우팅 |
| `worker-create-pr` | PR 본문 표준 템플릿 생성 및 gh CLI 연동 |
| `worker-implement-plan` | 설계 문서 기반 구현 실행 |
| `worker-resolve-review` | 리뷰 코멘트 분류 후 처리 |
| `worker-review-code` | 독립적 관찰자 역할로 PR 리뷰 |
| `worker-deploy-vercel` | 배포 자동화 |
| `orchestrator-review-loop` | 리뷰-수정 루프 자동 진행 |

외부 플러그인으로 추가 활용 중인 스킬: `vercel-*` (5종 — cli-with-tokens, composition-patterns, react-best-practices, react-native-skills, react-view-transitions), `web-design-guidelines` (1종). 사용자가 직접 만든 스킬은 아니지만 워크플로 내에서 참조됨.

### 6-3. 피드백 메모리 (15건)

실수로부터 학습해 재발을 막기 위한 규칙. 예시:

- React.FC 사용 금지, `({...}: Props)` 구조분해 형태
- 배열 타입은 `Array<T>`, `T[]` 금지
- Phase로 나눈 단일 작업은 **전체 종료 후 단일 PR**
- 리뷰 Suggestion은 Must Fix 아니어도 **반영/미반영 근거 필수**
- Registry 패턴 선호 — 타입별 분기를 중앙 집중
- 옵션 추천 시 다른 옵션 대비 장단점과 한계 명시
- 스킬 수정은 독립 워크트리에서

### 6-4. 규칙 문서화

[`docs/rules/`](../rules/) 하위에 토픽별로 분리:
- `collaboration/` — 작업 흐름·커뮤니케이션
- `typescript/` — 타입 작성 규칙
- `naming/` — 식별자 명명
- `commit-convention.md` — 커밋 포맷
- `plan-writing-guide.md` — 설계 문서 가이드

**핵심**: 규칙을 **스킬이 라우팅**하므로, 매번 사용자가 지시하지 않아도 상황에 맞는 규칙 문서가 자동으로 참조됩니다.

## 7. 활용 성숙도 평가

### 잘한 점

1. **방법론 자체를 Claude Code에 맞춰 재설계** — 단순 코드 생성 도구가 아닌 개발 워크플로의 일부로 통합
2. **스킬 생태계 구축** — 반복 작업(PR 생성, 리뷰 반영, 컨벤션 체크)의 셋업 시간 0에 수렴
3. **설계 문서 선행** — 누적 21건의 plan 커밋 (완료 후 삭제 운영). 짧은 세션에서 맥락 회복 비용 감소
4. **자동 리뷰 루프** — 오케스트레이터가 도는 동안 병렬 진행 가능
5. **피드백 메모리 축적** — 같은 실수 반복 방지
6. **규칙의 명문화·자동 라우팅** — 컨벤션을 개발자가 매번 상기시킬 필요 없음

### 개선 여지

1. **리팩터링 편중** — refactor 95 vs feat 23. 기반 정비에 비중이 쏠림
2. **초반 번복** — FSD 시도 후 Feature-First로 재편. "빠른 실험 → 빠른 철회"의 장점이지만 수작업 환산 시간이 부풀어오름
3. **규칙 뒤늦은 정착** — 컨벤션이 작업과 병행해 만들어진 탓에 초반 커밋은 재정비 대상

## 8. 결론

- **38시간 투입으로 408~712시간(중앙값 ~500h) 규모의 작업 완수** → 약 **10~13배 시간 효율** (중앙값 기준 13배)
- 절대적 가속보다 **"같은 시간에 훨씬 큰 스코프를 소화"**가 본질
- 자체 스킬·규칙·메모리 인프라가 구축되어 **지금부터는 가속이 더 커질 여지**가 있음 (셋업 비용 상각 완료)
- 다음 단계 제안: feat 비중을 높여 **포트폴리오로서의 콘텐츠**를 강화 (현재는 "잘 만든 플랫폼" 상태, "보여줄 프로젝트" 비중 추가 필요)
